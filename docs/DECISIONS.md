USL의 단순 바인딩 문법과 그 위의 CLI 기반 프로그램이라는 역할 분담을 유지하면서, 문법 자체의 표현량·전달량·메모리·AI 토큰 및 사용 비용을 설계 기준에 포함한다. 기술 조사와 실제 연결 fixture의 비교 결과를 표준 그래프의 요구·출처·근거로 연결한다.

**AI의 공학 기준:** 자원/의미/역할 선언 재사용, 원래 ID를 보존한 로컬 별칭, 복원 가능한 표·사전 표현, 공백 축소를 비교한다. 무손실 표현은 ID·역할·참조·metadata·출처와 해석 범위를 보존해야 한다. 특정 바이트 절감률을 토큰·heap·API 청구 절감률로 바꾸지 않고, 사전·복호화 설명의 비용과 수신자의 이전 문맥 보유 조건도 포함한다.

새 표기법은 round-trip과 tokenizer별 측정으로 이득을 확인한 뒤 선택적으로 검토한다. 저장/전송용 binary 압축, provider prompt cache, 손실이 있는 자연어 요약은 각각 별도 층으로 다룬다. 이번 오프라인 비교는 모델의 이해 정확도·실제 API 청구·도메인 기능 구현 또는 Lean 증명 완료를 뜻하지 않는다. [조사·측정·적용 기준](COMPACT_SYNTAX_RESEARCH.md).

## USL 위에 올라가는 CLI 기반 프로그램 — 2026-09-29

사용자 원문:

> 그게 가능하도록만 해주면되 문법적으로 그 너가 말한 수많은거는 cli 기반으로 프로그램 USL 기반 프로그램이 올려지는거고 ㅇㅇ 뭔말하는지 알겟지 ㅇㅇ?

USL은 그런 기능을 만들 수 있도록 연결을 문법적으로 표현하는 기초를 제공한다. 실제 기능은 **USL 위에 올라가는 CLI 기반 프로그램**이 구현한다. 앞선 가중치·계층·M 맵·HSWM 기능은 이 상위 프로그램의 기능이며, 필요한 선택 규칙도 그 프로그램이 사용하도록 USL로 연결한다.

AI의 구현 해석은 프로그램·자원·입출력·규칙의 참조를 의미·역할로 결속하는 표현력을 확인하고, 구체적인 소비 프로그램에서 드러난 문법적 부족만 보완하는 것이다. 세부 구문·프로그램 패키징·실행 방식은 이 발화에서 확정하지 않았다. 이번 변경은 역할 분담의 기록이며 새 runtime 구현은 아니다.

## USL은 문법, CLI는 그 문법을 사용하는 도구 — 2026-09-29

사용자 원문:

> USL 은 문법같은거고 그 cli 도구로 깔끔하게 동작하도록 하는게 맞을것같은데 그것도 어케생각하냐 표준 그래프 엔지니어링으로 정리좀 해줘봐봐 ㅇㅇ

USL의 문법·의미 연결 모델과 이를 사용하는 CLI를 중심으로 현재 구조와 다음 작업을 정리한다. 앞선 하이퍼그래프·가중치·M 맵·상하위 요구사항도 함께 연결한다. 기존 `.usl` 문법, TypeScript 입력, resource graph, 역할 기반 탐색, 바인딩, CLI는 구현 근거로 다루고, 의미 가중치 계산·M 맵·타입별 계층 탐색은 제안 상태로 구분한다.

**AI 설계 제안:** 입력을 순수한 역할 기반 하이퍼그래프 코어로 모으고, CLI를 코어와 소유자 adapter의 얇은 진입점으로 둔다. 가중치는 출처와 revision이 있는 주장으로, 상하위는 타입이 있는 관계로, M 맵은 재생성 가능한 파생 인덱스로 설계하는 방향을 제안한다. M의 정식 정의, 구체적인 weight·hierarchy schema와 갱신 정책은 사용자 확정 사항으로 표시하지 않는다.

요구사항·현재 코드 근거·AI 제안을 기존 resource graph와 JSON-LD/PROV-O, domain profile·SHACL로 기록하고, 미결정 schema·정책을 설계 문서에 남긴다. 그래프의 구조·출처 검사와 미래 기능의 동작 검증은 별개다. 이번 정리는 새 runtime 기능이나 해당 확장의 Lean 증명 완료를 뜻하지 않는다. [설계와 다음 작업](SYNTAX_CLI_GRAPH_ARCHITECTURE.md).

## 전체 저장소의 HSWM 연결 준비 조건 — 2026-09-29

> 내 모든 프로그램에 확장해줘 ㄴㄴ 우리프로젝트니까 우리프로젝트를 HSWM 적으로 사용하려면 필수사항이야 우리 모든 레포에 그 규칙 싹다 박아줘봐 ㅇㅇ 그 작업환경에 접근할수 잇어야 한다고 ㅇㅇ
