# USL과 Cypher의 역할과 비용

현재 USL이 Cypher 기반 KG보다 전반적으로 낫다는 근거는 없다. 이미 KG 안에
관계와 근거가 잘 정리되어 있다면 USL을 추가하는 비용이 더 클 수 있다.

Cypher는 그래프 조회·수정 언어이고, Neo4j는 이를 실행하며 데이터를 저장하는
DB다. 양방향 탐색과 관계 속성도 지원한다. 따라서 이 기능들을 USL만의 장점으로
소개하면 안 된다. [Neo4j 공식 소개](https://neo4j.com/docs/getting-started/cypher/)

| 목적 | 현재 USL의 범위 | Cypher 기반 KG와 비교 |
|---|---|---|
| 관계 저장·조회·집계 | 메모리 plan과 파일 아티팩트, 제한된 경로 탐색 | DB 저장·질의 기능을 대체하지 않음 |
| 의미·조건·검사 근거 표현 | 역할 타입, 설명, 적용 조건, 선언된 검사 | KG에서도 노드·속성·관계로 모델링 가능 |
| KG·Git·파일·URL 실제 관측 | 선택한 자원만 resolver로 읽고 버전·근거 기록 | 같은 관측 계층을 KG 위에 구현할 수 있음 |
| 오래된 연결 확인 | 주소·내용·의미 계약 digest를 분리해 비교 | 재사용 가능한 구현이 있다는 편의가 핵심 |
| AI 문맥 전달 | 경로의 역할·근거 보존, 출력 예산, 동일 digest 재전송 생략 | 쿼리 결과를 줄이는 방식과 비교 실험 필요 |
| 주소 한 곳 수정 | 공유 resource 이름을 참조하는 해당 plan의 링크에 반영 | 안정된 KG ID를 사용하는 방식도 가능 |

USL의 이점 후보는 새 문법의 표현력보다 **외부 자원 관측과 문맥 생성 로직을
여러 도구에서 재사용하는 비용 절감**이다. 기존 KG에 그 기능이 있다면 중복 계층을
추가할 이유가 약하다. 현재 KG resolver는 고정 `ontology_get` 인터페이스를 읽는다.
임의 Cypher 쿼리, Neo4j 저장소 backend, 양방향 DB 동기화는 구현되어 있지 않다.

`.usl`은 선택 가능한 선언 문법이다. TypeScript SDK로도 같은 plan을 만들 수 있다.
등록된 파일은 수정 시 자동 검증·교체하지만, 거대한 단일 파일은 변경할 때 그 파일
전체를 다시 컴파일한다. 캐시가 DB 인덱스나 질의 최적화를 대신하지 않는다.
Neo4j에는 별도의 [질의 계획·튜닝 체계](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/)가 있다.

한 게임 기능에서 같은 과제를 비교해야 도입 효과를 판단할 수 있다. 동일한 KG·코드·
사양 자료와 모델을 사용하고, Cypher로 필요한 결과만 반환하는 기준선에도 문맥 캐시를
허용한다. 참조를 찾는 시간, 낡은 근거 검출 수, 불필요한 재검사 수, 실제 모델 입력·출력
토큰, 설정·유지 비용을 함께 잰다. 기존 `GAME_WORKFLOW`는 격리 fixture 검사이며
Cypher 대비 성능이나 실제 모델 토큰 우위를 입증한 실험이 아니다.

현재 도입 판단: KG 내부 질의가 목적이면 기존 Cypher를 활용한다. 서로 다른 외부
자원을 같은 정책과 관측 보고서로 다루는 반복 작업이 있을 때 USL의 재사용 효과를 평가한다.
